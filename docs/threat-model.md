# Threat Model and Detection Logic

_This document outlines the target NIDS lab scenarios, expected network behaviors, and the foundation for our alert and risk-scoring systems. It serves as the data contract between the Cybersecurity, Data/ML, and DevOps roles._

## 1. Normal Baseline Behaviour

- **Definition:** The standard, expected traffic patterns generated by routine operations within the NIDS lab environment.
- **Expected Network Behaviour:** Normal connection requests, standard packet sizes, and typical transaction frequencies that do not trigger high-severity alerts.
- **Team Impact:** The ML Engineer will use this baseline to establish normal traffic patterns for training, while the Cybersecurity Engineer will use it as the control state to design rules that minimize false positives.

## 2. Selected Attack Categories & Expected Behaviour

_Note: All simulations must remain strictly within the isolated VMs/lab network the team has configured and has explicit permission to test.

### A. Port / Reconnaissance Scan

- **Objective:** Identify active devices, open ports, and potential vulnerabilities on the target machine.
- **Expected Network Behaviour:** An unusual connection or port-probing pattern.
- **Simulation & Detection (Network/Cyber Roles):** The Network Engineer will simulate this using tools like Nmap. Security rules will monitor for a single source IP initiating SYN requests to a wide range of ports over a short time window.

### B. Brute-Force Login Simulation

- **Objective:** Gain unauthorized access by systematically guessing passwords.
- **Expected Network Behaviour:** Repeated failed authentication attempts directed at a specific service.
- **Simulation & Detection (Network/Cyber Roles):** Rules will flag a high concentration of failed login events originating from a single attacker machine within a defined time limit.

### C. Controlled Denial-of-Service (DoS) Traffic

- **Objective:** Exhaust target resources to disrupt normal operations within the isolated lab.
- **Expected Network Behaviour:** An abnormally high request or packet rate flooding the target.
- **Simulation & Detection (Network/Cyber Roles):** Detection will rely on volumetric thresholds, identifying massive statistical deviations from the established baseline traffic volume.

## 3. Severity Levels & Risk Scoring Model

To help the dashboard prioritize alerts, the NIDS will evaluate detected events using the following framework.

**Risk Formula:** `Risk = Likelihood × Impact × Exposure`.

- **Likelihood:** The probability that the event is a genuine attack, derived from ML confidence scores or rule strictness.
- **Impact:** The potential damage of the attack class (e.g., DoS disrupting the network versus a passive port scan).
- **Exposure:** The vulnerability or criticality of the target asset within our lab topology.

## 4. Alert Schema & Triage States (DevOps Integration)

When the detection layer identifies suspicious behavior, it will send a structured alert to the API/Database. DevOps (Person 5) must ensure the database schema accommodates the following required fields[cite: 2, 3]:

- **Timestamp**
- **Alert ID**
- **Detection Source:** ML / Rule / Both
- **Predicted/Identified Category:** (e.g., Reconnaissance, Brute-Force, DoS)
- **Severity:** (e.g., Low, Medium, High)
- **Risk Score:** (Calculated via the formula above)
- **Relevant Traffic/Event Features:** The packet evidence
- **Confidence/Probability:** (Particularly for ML model outputs)
- **Recommended Analyst Action**

**Dashboard Triage States:** Alerts will enter the dashboard in an "investigation required" state and can be updated to "triaged" once reviewed by a team member.
